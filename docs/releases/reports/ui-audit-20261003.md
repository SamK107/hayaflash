# Audit UI / texte — anglais résiduel, émojis-icônes, devises non-FCFA

- **Date** : 2026-10-03
- **Branche** : `audit/ui-text-currency` (créée depuis `main`, HEAD `d6eb0c6`)
- **Nature** : audit **lecture seule** — aucun fichier applicatif (template, `.py`, `.js`) modifié ; seul ce rapport est ajouté.
- **Périmètre** : `templates/**/*.html` (56), `static/js/hf-*.js` (7), 175 fichiers `.py` applicatifs suivis par git (hors migrations, tests, scripts, commandes de gestion). `static/vendor/`, `.venv/`, `Claude outputs/` (copies de sauvegarde) et `media*` exclus.
- **Méthode** : parcours AST Python (littéraux de chaîne hors docstrings), analyse regex des nœuds texte / attributs / littéraux JS des templates, croisement avec l’usage de Lucide par gabarit. Les résultats sont une **heuristique** : les chaînes anglaises ne contenant aucun mot-clé repérable ont pu échapper au scan (voir « Limites »).

**Constats clés**

1. **Aucune internationalisation en place** : `USE_I18N = True` et `LANGUAGE_CODE = "fr-fr"` (`config/settings/base.py:305-307`), mais **aucun** `locale/`, `.po`/`.mo` du projet, aucun `gettext`/`gettext_lazy`, aucun `{% trans %}`/`{% blocktrans %}`, pas de `LocaleMiddleware`. Tout est en dur en français ; l’anglais résiduel vient exclusivement de chaînes codées en dur côté services/API.
2. **Le défaut le plus visible** : le formulaire de commande public (`hf-public.js`, `this.orderError = Object.values(data).flat()[0]`) affiche **le premier message d’erreur de l’API tel quel**. Les validations de `orders/services/client_order.py`, `create_order.py` et `delivery/services/validation.py` étant en anglais, un acheteur malien peut voir « Address must be at least … », « Insufficient stock for product … », « Provide a written address or record a voice note. », « Too many order attempts … ».
3. **Aucun `$`, `€`, `£`, `USD`, `EUR` monétaire** dans les templates, le JS ou les chaînes Python affichées. Les 67 `$` présents dans `templates/` + `static/js/` sont tous techniques (voir C.1). `XOF` n’apparaît que comme code ISO légitime (Orange Money, JSON-LD `priceCurrency`).
4. **Émojis** : 6 gabarits utilisent des émojis comme pictogrammes UI ; **6 sur 6 mélangent aussi Lucide** dans la même page ; 35 gabarits utilisent Lucide. `core/home.html` concentre l’essentiel (27 des 36 émojis-icônes UI).

**Recommandation de périmètre (PR)** — découper en **3 PR indépendantes**, par thème et par risque :

1. **PR « textes FR parcours acheteur »** (priorité haute, petit diff) : `orders/services/client_order.py`, `create_order.py`, `delivery/services/validation.py`, `orders/api.py:35`, OTP (`otp.py:104`). Attention au **couplage** sur la chaîne `"Too many order attempts"` (détection 429) et aux **tests** qui assertent ces messages anglais (`analytics/tests.py`, `delivery/tests.py`, `payments/tests_services.py`) — à mettre à jour dans la même PR.
2. **PR « libellés restants »** (priorité moyenne) : espace vendeur (`delivery/views.py`, `orders/views.py`, `delivery/services/*`), libellés `TextChoices`/`help_text`/`verbose_name` (payments, analytics, accounts), « Dashboard », « Staff Only », API JSON. Décision préalable : introduire `gettext_lazy` + `locale/fr` maintenant, ou rester en français en dur (cohérent avec le choix actuel).
3. **PR « icônes + FCFA »** (priorité basse, purement présentation) : remplacer les émojis-icônes par Lucide (home.html en dernier, c’est du marketing), harmoniser « F » → « FCFA » (3 gabarits), ajouter l’unité manquante (COD, admin plateforme), aligner le séparateur de milliers WhatsApp.

Tout faire en une PR est déconseillé : la PR 1 touche à la logique de validation + tests, la PR 3 est un gros diff de gabarits sans risque fonctionnel ; les mélanger ralentit la revue.

### A.2 Origine des messages (a / b / c)

- **(a) Chaînes en dur en anglais dans le code HayaFlash** : toutes les lignes du tableau A.3 (hors ligne navigateur).
- **(b) Messages par défaut Django/DRF non surchargés** : **aucun problème constaté**. Avec `LANGUAGE_CODE = "fr-fr"` et sans `LocaleMiddleware`, la langue active est toujours le français ; Django et DRF livrent leurs traductions `fr` (validateurs de mot de passe, `required`, `max_length`…). Les `serializers.CharField(...)` sans `error_messages` renvoient donc du français. Point d’attention : les champs de modèle **sans `verbose_name`** (ex. `User.phone`, `email`, `display_name`) apparaissent avec le nom de champ anglais dans l’admin.
- **(c) Bibliothèques tierces** : `django-axes` — message de blocage **surchargé en français** (`AXES_LOCKOUT_MESSAGE`, `base.py:443`, réponse JSON/HTML via `core/services/axes_hooks.py`) ; axes embarque aussi une locale `fr`. Seul cas tiers anglophone : `err.message` natif du navigateur concaténé dans `hf-seller.js:91`.

### C.3 Montants réels : « FCFA » partout ?

Contrôle automatique sur les gabarits : toute expression `{{ … price|prix|total|amount|montant|cod|revenue|ca|subtotal|commission|gain … }}` a été comparée à la présence de « FCFA » dans les lignes voisines (−1/+2).

- **30 rendus de montants** portent bien « FCFA » à proximité (produits, commandes, abonnements, paiements, checkout, quota, KPI vendeur, page publique).
- Anomalies (cf. C.2) : « F » seul ×3, unité absente ×2 groupes (COD, admin plateforme). Les autres lignes signalées par le contrôle sont des **compteurs** (nombre de commandes, de vendeurs…) ou des variables JS (`price:` dans `client_order.html:82`, affiché plus bas avec « FCFA » à la ligne 50) — faux positifs.
- JS : `hf-components.js:171` et `flash_sale_public.html:462, 593` formatent en `toLocaleString('fr-FR') + ' FCFA'` ✓.
- Aucun gabarit composant générique n’impose un symbole par défaut.

## Section D — Cohérence avec RM-12 (`docs/releases/v1.0.0-rc1.md`)

RM-12 : « Montants en FCFA entiers, jamais de centimes, jamais ×/÷ 100 » — tracé ✅ avec preuves sur le **modèle de données** : `DecimalField(decimal_places=0)` (`orders/models.py:68`, `:98` ; `products/models.py:33`, `:149`, `:236` ; `payments/models.py:39`, `:74` ; `delivery/models.py:68`) et `PositiveIntegerField` (`subscriptions/models.py:129`).

**Cet audit ne contredit pas RM-12.** Résultats : aucun symbole `$`/`€`/`£` ni division/multiplication par 100 liée à l’affichage n’a été trouvé ; les montants sont affichés en entiers (`floatformat:0` / `"0g"`, `thousands`). Les anomalies de la section C.2 (« F » au lieu de « FCFA », unité absente, séparateur virgule dans WhatsApp) sont **exclusivement des problèmes de template/présentation**, pas de modèle de données ni de règle métier : les valeurs sous-jacentes sont correctes (entiers FCFA). Aucune mise à jour du statut RM-12 n’est requise.

## Limites de l’audit

- Détection d’anglais **heuristique** (mots-clés + absence de marqueurs français) : une phrase anglaise sans mot-clé commun peut manquer ; les ~110 chaînes sans marqueur français restantes ont été relues manuellement.
- Le chemin d’affichage exact des erreurs HTMX (4xx) côté vendeur n’a pas été vérifié par exécution ; ces lignes sont donc classées « mineur — à confirmer ».
- Aucun test d’exécution (pas de rendu navigateur) : audit statique uniquement.
- Les tests existants qui assertent des messages anglais (`analytics/tests.py`, `delivery/tests.py`, `payments/tests_services.py`, `core/tests_gitattributes.py`) sont à passer en revue avant toute correction.
